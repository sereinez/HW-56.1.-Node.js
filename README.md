# async-operation-demo

Демонстрація функції `asyncOperationDemo`, яка ілюструє порядок виконання
трьох асинхронних API Node.js — `process.nextTick`, `setImmediate` та
`setTimeout(0)` — у межах циклу подій (event loop).

## Вміст проєкту

```
async-demo/
├── asyncOperationDemo.js       # сама функція
├── index.js                    # приклад запуску (демо-скрипт)
├── asyncOperationDemo.test.js  # тести на Jest
├── package.json
└── README.md
```

## Встановлення

```bash
npm install
```


## Запуск демо

```bash
npm start
```

Очікуваний вивід у консолі:

```
Перший виклик
Останній виклик
Виконано nextTick
Завершено виконання: nextTick
Виконано setImmediate
Завершено виконання: setImmediate
Виконано setTimeout
Завершено виконання: setTimeout
```

## Запуск тестів

```bash
npm test
```

Проєкт написаний як ES-модуль (`"type": "module"` у `package.json`), тому
тести запускаються через експериментальну підтримку ESM у самому Node.js
(без Babel):

```
node --experimental-vm-modules node_modules/.bin/jest
```

Це вже прописано у скрипті `test`, тож достатньо `npm test`.

## Чому саме такий порядок виконання?

1. **Синхронний код виконується першим.** Виклики `process.nextTick`,
   `setImmediate` і `setTimeout` лише *планують* асинхронні операції — вони
   нічого не виконують одразу. Тому спершу в консоль потрапляють
   `"Перший виклик"` і `"Останній виклик"` — обидва логуються синхронно,
   до того як стек викликів звільниться.

2. **`process.nextTick` виконується найпершим.** Після того як поточна
   операція (тіло функції) завершилась, Node.js спочатку повністю спорожняє
   черзу `nextTick`, і лише потім переходить до фаз циклу подій (`timers`,
   `poll`, `check` тощо). Тому `nextTick`-колбек гарантовано відпрацьовує
   раніше за `setImmediate` і `setTimeout`.

3. **`setImmediate` виконується у фазі `check`.** Ця фаза йде одразу після
   фази `poll` в кожній ітерації циклу подій.

4. **`setTimeout(0)` виконується у фазі `timers`.** Навіть із затримкою `0`
   мс, таймер спрацьовує в наступній ітерації циклу подій, і на практиці —
   коли код виконується в основному модулі (а не всередині I/O-колбека) —
   зазвичай пізніше за `setImmediate` (хоча Node.js офіційно не гарантує
   сталий порядок між `setImmediate` і `setTimeout(0)`, коли вони плануються
   поза I/O-циклом; гарантії, які наведені у файлі, стосуються насамперед
   `nextTick`, який завжди виконується першим).

## API функції

```ts
function asyncOperationDemo(
  callback: (operation: 'nextTick' | 'setImmediate' | 'setTimeout') => void
): void
```

- **Параметри:**
  - `callback` — функція, яка буде викликана окремо після завершення
    кожної з трьох асинхронних операцій, з відповідним ідентифікатором
    (`'nextTick'`, `'setImmediate'` або `'setTimeout'`).
- **Помилки:** якщо `callback` не передано або це не функція, синхронно
  кидається `TypeError`.
- **Логування:** усередині функції логуються `"Перший виклик"`,
  `"Останній виклик"` та по одному повідомленню `"Виконано <операція>"`
  для кожної асинхронної дії. Повідомлення `"Завершено виконання:
  [operation]"` логується у прикладі використання (`index.js`) — саме
  так, як було задано в технічному завданні: воно виводиться колбеком,
  переданим у `asyncOperationDemo`.

## Покриття тестами (Jest)

Файл `asyncOperationDemo.test.js` перевіряє:

1. Що функція кидає `TypeError`, якщо `callback` відсутній або не є
   функцією.
2. Що `"Перший виклик"` і `"Останній виклик"` логуються синхронно й у
   правильному порядку.
3. Що `callback` викликається рівно тричі — по одному разу на кожну
   операцію.
4. Що `process.nextTick` завершується першим серед асинхронних операцій.
5. Що для кожної операції формується повідомлення виду
   `"Завершено виконання: [operation]"`.

Тести мокують `console.log` через `jest.spyOn`, щоб не забруднювати вивід
і водночас перевіряти саме те, що й коли логується.
